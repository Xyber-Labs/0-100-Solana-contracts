\section*{TL;DR}
\begin{itemize}
  \item \textbf{LaunchPool (Per-Wallet Cap):} Standardized per-wallet limit $C{=}\Ccap$\,SOL; overflow handled by VRF lottery with auto-prepared refunds (one-click claim).
  \item \textbf{Creator Self-Snipe with Vesting:} Creator may self-deposit up to $S_{\max}{=}\CreatorSnipeMax$\,SOL; each SOL adds $\VestingPerSolHours$\,h to creator vesting linearly (pro-rata), up to $T_{\text{vest,max}}{=}\CreatorSnipeMax$ days.
  \item \textbf{VRF Selection (Overflow Only):} If demand exceeds hard cap $H$, allocation uses uniform VRF-backed sampling over \emph{ticketized} deposits.
  \item \textbf{VRF-Timed LP Window:} After selection finalization, a VRF draw picks an exact deploy time in a fixed $+\LPWinStart$\,h to $+\LPWinEnd$\,h window.
  \item \textbf{Economics:} Platform-fee buybacks market-buy \textdollar XYB (80\%) and fund treasury (20\%); the \emph{Creator Share} is paid only from DEX trading fees after listing with a \emph{dynamic split by market-cap bands} (see Appendix). Payouts follow the asset rule: SOL-fee proceeds to Xyber, token-fee proceeds to the creator (periodic harvest to a creator payout vault).
  \item \textbf{Single preset:} One standardized configuration (no creator-side tuning). Sale tokens are claimable after LP deploy; users have no vesting/cliff.
\end{itemize}

\section*{Introduction}
Open, decentralized token launches often suffer from gas wars, bot sniping, and opaque allocation rules. 0--100 focuses on five primitives—\emph{per-wallet caps}, \emph{VRF-backed overflow selection}, \emph{VRF-timed LP deployment}, \emph{creator self-snipe with vesting}, and \emph{platform-fee \textdollar XYB buybacks with a post-listing Creator Share}—to deliver fairer distributions and reduce adversarial dynamics while staying minimal and auditable.

\section*{Design Principles}
\begin{itemize}
  \item \textbf{Single preset:} One standardized configuration; no creator-side tuning.
  \item \textbf{Fairness-by-design:} A hard per-wallet cap $C$ and uniform ticket-level selection eliminate gas races and mempool games.
  \item \textbf{Minimal \& auditable:} Small, self-contained programs with deterministic state transitions and explicit authority separation (program-derived addresses).
  \item \textbf{Provable randomness:} Chain-oracle VRF for selection and LP time draws; blockhash-only RNG is \emph{not} used.
  \item \textbf{Transparent economics:} Platform-fee buybacks market-buy \textdollar XYB; the Creator Share is paid only from DEX trading fees after listing (dynamic split by market-cap bands; SOL fees to Xyber, token fees to creator; 80/20 platform-fee policy for $XYB$ buybacks/treasury).
  \item \textbf{Canonical pool commitment:} The launch precommits DEX pool parameters; the deploy instruction verifies the commitment to prevent fake-pool front-runs.
\end{itemize}

\section*{System Overview}
\textbf{Actors:} Contributors, Launch Creators, 0--100 Protocol, DEX LP.

\textbf{Lifecycle:}
\begin{enumerate}[label=\arabic*)]
  \item \emph{Create Launch:} Initialize with standardized parameters: $H{=}\Hcap$\,SOL, $C{=}\Ccap$\,SOL, ticket size $\tau{=}\TauVal$\,SOL, funding period $T_{\text{fund}}{=}\FundHours$\,h, LP window $+\LPWinStart$\,h to $+\LPWinEnd$\,h; supply split Sale \SalePct\% / LP \LPPct\%. A canonical hash of LP parameters is committed.
  \item \emph{Funding Opens:} Wallets deposit up to $C$; deposits are \emph{ticketized} in increments of $\tau$.
  \item \emph{Selection (if oversubscribed):} VRF-driven uniform sampling approves up to capacity $K=\lfloor H/\tau \rfloor$ tickets; unselected amounts are prepared for refund.
  \item \emph{Sale Allocation \& Claim:} Approved amounts map proportionally to the Sale bucket. Sale tokens have \emph{no vesting/cliff} and become claimable after LP deploy.
  \item \emph{Randomized LP:} A second VRF draw sets $t^\ast \in [+6\text{h}, +18\text{h}]$ after selection finalization; at or after $t^\ast$, anyone may initialize the precommitted Raydium pool.
  \item \emph{Post-Listing Fees:} Platform fees are used to market-buy \textdollar XYB (80\%) and fund treasury (20%). Trading fees from the Xyber LP position are harvested and split \emph{dynamically by market-cap bands} (Appendix), with SOL-fee proceeds routed to Xyber and token-fee proceeds to the creator payout vault on a governance-set cadence.
\end{enumerate}

\section*{Core Mechanics}

\subsection*{Creator Self-Snipe \& Vesting Extension}
A launch creator may deposit up to $S_{\max}{=}\CreatorSnipeMax$\,SOL into their own pool (outside the public per-wallet cap). For each SOL deposited, the vesting period for the creator allocation increases linearly by $\VestingPerSolHours$ hours per SOL. Let $s \in [0, S_{\max}]$ be the creator's self-snipe in SOL. The vesting time applied to the creator allocation is
\[
T_{\text{vest}}^{\text{creator}} = \VestingPerSolHours\,\text{h} \cdot s\,.
\]
No flooring is applied; fractional SOL extend vesting proportionally. Because $s \le S_{\max}$ and $S_{\max}{=}\CreatorSnipeMax$, it follows that $T_{\text{vest}}^{\text{creator}} \le \CreatorSnipeMax$ days. Self-snipe funds are treated as standard deposits for price discovery and LP formation; the vesting applies only to the creator's token claim. The self-snipe uses a dedicated instruction exempt from the public cap $C$ and gated by creator authority.

\subsection*{Capped Wallet Funding Pool}
Per-wallet cap $C$ is enforced on-chain. Deposits must be in exact multiples of the ticket size $\tau$; any non-multiple is \emph{immediately refunded in the same transaction}. Let a deposit amount be $\text{amount}_i = m_i\,\tau$ with integer $m_i \ge 0$. The number of tickets minted in this deposit is
\[
k_i = \min\!\left( m_i,\; \left\lfloor \frac{C - \text{deposited}_i}{\tau} \right\rfloor \right),
\]
where $\text{deposited}_i$ is the wallet's cumulative accepted deposit before this transaction. Receipts are issued to each wallet for the number of tickets minted.

\subsection*{Overflow + Randomized Allocation}
If $\sum n_i \cdot \tau \le H$, all tickets are approved. If oversubscribed, define capacity $K = \left\lfloor \frac{H}{\tau} \right\rfloor$ and uniformly sample $K$ tickets without replacement from the multiset of all tickets using a VRF-derived seed. For wallet $i$, selected tickets $y_i$ define approved amount $a_i = y_i \cdot \tau$ and refund $r_i = \text{deposit}_i - a_i$.

\subsection*{Selection Probability (at least one ticket)}
Let total ticket count be $N$ and capacity $K=\lfloor H/\tau \rfloor$. A wallet with $n_i$ tickets has probability of at least one selection:
\[
\mathbb{P}(Y_i \ge 1) = 1 - \frac{\binom{N - n_i}{K}}{\binom{N}{K}}\,, 
\]
Tickets are \emph{non-transferable} (receipt mints are bound to the depositing wallet); they only confer selection and claim rights to that wallet.
by the hypergeometric model.

\subsection*{Sale Allocation \& Claim}
Let $A_{\text{sale}}$ denote the Sale bucket (54.054\% of total supply). Each approved wallet $i$ receives
\[
\text{tokens}_i = \frac{a_i}{\sum_j a_j} \cdot A_{\text{sale}}\,.
\]
Sale tokens have no vesting or cliff; claims open immediately after LP deploy.

\subsection*{Randomized LP Creation (Raydium baseline)}
The creator precommits an LP deployment window of $+\LPWinStart$\,h to $+\LPWinEnd$\,h after selection finalization. A VRF draw sets $t^\ast$ inside this window. Anyone can execute LP deployment at or after $t^\ast$ with precommitted parameters on Raydium. Initial price is set by the pair ratio:
\[
P_0 = \frac{\text{base}_{\text{LP}}}{\text{token}_{\text{LP}}}\,.
\]
\textbf{Canonical pool commitment:} The launch precommits a hash of LP parameters (token mints, fee tier, initial price ratio, pool program) and the expected pool address derivation; the deploy transaction verifies the commitment before initializing.

\textbf{Randomness fallback:} If VRF is temporarily unavailable, the system retries; on repeated failure the window defaults to $+0$\,h to $+\LPFallbackEnd$\,h.

\textbf{Who executes deploy \& how they are paid:}
In practice, any third party submits the deploy transaction at/after $t^\ast$. The submitter receives a small, capped \emph{LP-token bounty} as an execution fee. This bounty comes from the LP side (\emph{not} from Sale) and does not change contributor claims.
 
\subsection*{Built-in Anti-Snipe}
Because allocations are decided before trading, launch-time sniping has limited impact on initial distribution. Randomized LP timing further reduces coordinated positioning around the deploy moment.

\subsection*{Fee Model: \textdollar XYB Buybacks \& Creator Share}
\textbf{Platform-fee buybacks.} Xyber platform fees from DEX trades are allocated \emph{80\% to market-buy \textdollar XYB} and \emph{20\% to the Xyber Treasury}. Routing is policy-controlled; cumulative totals and balances are publicly reported.

\textbf{Creator Share from trading fees.} After listing, DEX trading fees accrue to the Xyber LP position and are harvested on a governance-defined cadence. Each harvest applies the \emph{dynamic split by market-cap bands} (Appendix). Payouts follow the asset rule: \emph{SOL-fee proceeds are routed to Xyber}, while \emph{token-fee proceeds are routed to the creator payout vault}.

\subsection*{Dynamic Fee Split (Market-Cap Bands)}
We use a \emph{market-cap–based dynamic split} of the trade commission between the \textbf{Creator} and the \textbf{Protocol (Xyber)}. The split is \emph{DEX-agnostic}:
\begin{itemize}
  \item on \textbf{Raydium} --- via \emph{harvest \& split} of LP commissions;
  \item on the \textbf{proprietary DEX} --- applied \emph{per-swap}.
\end{itemize}

Let the DEX \emph{trade commission} be the 100\% pool collected for a swap. The share sent to Creator vs.\ Xyber is determined by the project's \textbf{market cap (in SOL)} and the band it falls into. Bands provide hysteresis (band~1 includes a buffer above the hard cap 450 to protect early-stage liquidity).

\section*{On-Chain Architecture}
\textbf{Programs}
\begin{itemize}
  \item \textbf{FundingPool:} Configuration \& state accounts storing $H$, $C$, $\tau$, funding period, LP window, status; accepts deposits; mints ticket receipts.
  \item \textbf{RandomSelection:} Requests VRF, samples $K$ tickets, emits approvals, and prepares refunds.
  \item \textbf{DistributionVault:} Holds project tokens; maps approved amounts to Sale distributions; opens claims after LP deploy.
  \item \textbf{LPDeployer:} Verifies canonical pool commitment; after $t^\ast$, enables permissionless pool initialization via a CPI into Raydium.
  \item \textbf{FeeCollector \& Buyback:} Accrues platform fees; executes market buybacks of \textdollar XYB; publishes cumulative totals/balances.
  \item \textbf{DEXFeeHarvester \& CreatorPayout:} Harvests LP trading fees and applies the dynamic split by market-cap bands; routes SOL-fee proceeds to Xyber and token-fee proceeds to the creator payout vault; emits accounting events.
\end{itemize}

\textbf{Accounts \& Authorities (Sketch):}
\begin{itemize}
  \item Program-derived authority for FundingPool operations and LP deployment.
  \item Separate authority for FeeCollector/Harvester to execute buybacks and splits.
  \item Deterministically derived state accounts for per-launch configuration and per-wallet receipts.
\end{itemize}

\section*{Algorithms (Pseudocode)}

\subsection*{Deposit \& Ticketization}
\begin{code}
function deposit(wallet, amount):
  require(state == FundingOpen)
  require(amount % tau == 0)                // only multiples of tau accepted
  require(deposited[wallet] + amount <= C)  // enforce per-wallet cap
  tickets_new = amount / tau
  deposited[wallet] += amount
  tickets_issued[wallet] += tickets_new
  mint TicketReceipts(wallet, tickets_new)
\end{code}

\subsection*{Randomized Allocation}
\begin{code}
function run_selection():
  K = floor(H / tau)
  N = total_tickets()
  if N <= K:
    approve all tickets; finalize
  else:
    seed = get_vrf_seed()    // distinct request id
    winners = sample_without_replacement(N, K, seed)
    for each wallet i:
      y_i = count_winner_tickets(wallet i)
      a_i = y_i * tau
      approve(wallet i, a_i)
      refund_ready(wallet i, deposited[i] - a_i)  // no sub-tau remainder (deposits are multiples of tau)
\end{code}

\subsection*{Sale Allocation Calculation}

function compute_sale_allocation(wallet i):
  tokens_i = (approved[i] / total_approved) * A_sale
  // Claims open after LP deploy

\subsection*{Randomized LP Deployment}
\begin{code}
function schedule_lp():
  // +6h to +18h window after selection finalization
  start_offset = 6 * HOUR
  window = 12 * HOUR
  seed2 = get_vrf_seed()   // distinct or derived
  t* = selection_finalized_time + start_offset + (seed2 mod window)
  store t*
function deploy_lp():
  require(blocktime >= t*)
  verify_canonical_pool_commit()
  initialize_pool(token_LP, base_LP, price_ratio)
\end{code}

\section*{Security \& Risk}
\begin{itemize}
  \item \textbf{Verifiable randomness:} Oracle VRF proofs for selection and LP timing; commit-reveal fallback only as reserve path.
  \item \textbf{Uniform ticket fairness:} Selection is uniform at the ticket level; contribution helps only up to $C$.
  \item \textbf{Canonical pool commitment:} Precommitted hash and address verification to block fake-pool attacks.
  \item \textbf{Economic guardrails:} Pull-then-claim refunds; bounded instruction compute; deterministic authorities.
  \item \textbf{LP tokens:} Protocol-owned LP handled per configured policy (burn/lock if enabled); actions are irreversible and logged.
  \item \textbf{Upgrades \& observability:} Timelocked releases; exhaustive program logs/events; emergency halt path to safe refund-only states.
\end{itemize}
