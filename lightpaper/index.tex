\section*{TL;DR}
\begin{itemize}
  \item \textbf{Capped Wallet Funding Pool:} Each wallet contributes up to per-wallet cap $C$; the launch targets hard cap $H$.
  \item \textbf{Overflow + Randomised Allocation:} If demand $>$ $H$, we allocate by \emph{ticketized}, verifiably random selection; excess is auto-refunded.
  \item \textbf{Immediate Engagement Hub:} Funding start instantly unlocks 5--10 quests to build hype and score for redistributions.
  \item \textbf{Token Airdrop:} Selected participants receive tokens proportional to their \emph{approved} contribution.
  \item \textbf{Randomised LP Creation:} LP on an open DEX (e.g., Raydium) is deployed at a random time within a configured window.
  \item \textbf{Built-in Anti-Snipe:} Allocations precede trading; launch-time sniping is materially reduced; price MEV risk at listing can persist.
  \item \textbf{Optional LBP Purchase + Redistribution:} Optional liquidity bootstrapping purchase at LP with bounded limits; tokens redistributed via quests or cross-platform airdrops.
  \item \textbf{Lumi Revenue Model:} Lumira receives a small \% of each launch's supply; \emph{all} platform fees are used to buy back the Xyber token.
  \item \textbf{Agent-Optional Launches:} Works for meme coins and agent-powered projects; agents are an opt-in composable layer.
\end{itemize}

\section*{Introduction}
Open, decentralized launches are often dominated by bots and insiders. Retail contributors either miss allocations or chase volatile listings. Lumi addresses this with per-wallet caps, provable randomness, and an engagement-first experience that channels hype into measurable growth and fairer distribution.

\section*{Design Principles}
\begin{itemize}
  \item \textbf{Fairness-by-design:} Hard per-wallet cap + verifiable randomness $>$ gas wars and mempool games.
  \item \textbf{Hype with purpose:} Quests incentivize creation, learning, and community without extractive spam.
  \item \textbf{Simplicity \& composability:} Minimal, auditable contracts; permissionless where safe.
  \item \textbf{Transparent economics:} Fees and supply policies are pre-declared; fees route to Xyber buybacks.
\end{itemize}

\section*{System Overview}
\textbf{Actors:} Contributors, Launch Creators, Lumi Protocol, (optional) Agents, DEX LP.

\textbf{Lifecycle (MVP):}
\begin{enumerate}[label=\arabic*)]
  \item \emph{Create Launch:} Creator configures $H$, $C$, ticket size $\tau$, LP window $[t_{\text{start}}, t_{\text{end}}]$, and token allocations.
  \item \emph{Funding Opens:} Deposits up to $C$; Engagement Hub quests unlock.
  \item \emph{Selection:} If oversubscribed, run VRF-backed sampling of tickets to capacity.
  \item \emph{Airdrop Assignment:} Tokens proportional to approved contributions.
  \item \emph{Randomised LP:} LP deployable at VRF-drawn time $t^\ast$ inside the window.
  \item \emph{Trading \& Optional LBP Purchase:} Optional bounded liquidity bootstrapping purchase and redistribution.
  \item \emph{Post-Launch:} Fees route to Xyber buybacks; quests and agents continue evolving the community.
\end{enumerate}

\section*{Core Mechanics}

\subsection*{Capped Wallet Funding Pool}
Per-wallet cap $C$ is enforced on-chain; multiple deposits allowed while cumulative $\le C$. The launch targets a hard cap $H$ in base asset. Deposits are \emph{ticketized} by atomic size $\tau$:
\[
n_i = \left\lfloor \frac{\min(\text{deposit}_i, C)}{\tau} \right\rfloor
\]
with any remainder $< \tau$ held and later refunded if unused.

\subsection*{Overflow + Randomised Allocation}
If $\sum n_i \cdot \tau \le H$, all tickets are approved. If oversubscribed, define capacity $K = \left\lfloor \frac{H}{\tau} \right\rfloor$ and uniformly sample $K$ tickets without replacement from the multiset of all tickets using a VRF-derived seed. For wallet $i$, the selected tickets $y_i$ define approved amount $a_i = y_i \cdot \tau$ and refund $r_i = \text{deposit}_i - a_i$.

\subsection*{Selection Probability (at least one ticket)}
Let total ticket count be $N$ and capacity $K=\lfloor H/\tau \rfloor$. A wallet with $n_i$ tickets has probability of winning at least one selection:
\[
\mathbb{P}(Y_i \ge 1) = 1 - \frac{\binom{N - n_i}{K}}{\binom{N}{K}}\,.
\]
This follows the hypergeometric model with uniform sampling without replacement.

\subsection*{Immediate Engagement Hub}
At funding start, 5--10 quests unlock (e.g., follows/verify, content creation, meme contests, referrals, on-chain tasks, lore quizzes). Points contribute to future redistributions or micro-airdrops. Optional sybil friction includes allowlists, liveness checks, or social-graph scores.

\subsection*{Sybil Controls (Optional)}
Per-wallet caps alone do not prevent many-wallet strategies. Optional layers include allowlists, proof-of-personhood or social-graph scores, identity staking, and per-entity ticket caps. Creators can enable these gates depending on compliance and community needs.

\subsection*{Airdrop of Selected Participants}
Let $A_{\text{airdrop}}$ be the airdrop pool. Each approved wallet $i$ receives
\[
\text{tokens}_i = \frac{a_i}{\sum_j a_j} \cdot A_{\text{airdrop}}
\]
Optional vesting: cliff $T_{\text{cliff}}$ then linear over $T_{\text{vest}}$.

\subsection*{Randomised LP Creation (e.g., Raydium)}
The creator commits an LP window $[t_{\text{LP\_start}}, t_{\text{LP\_end}}]$. A VRF draws $t^\ast \in [t_{\text{LP\_start}}, t_{\text{LP\_end}}]$. Anyone can execute LP deployment at or after $t^\ast$ with precommitted parameters. Initial price is set by the pair ratio:
\[
P_0 = \frac{\text{base}_{\text{LP}}}{\text{token}_{\text{LP}}}
\]
Policy for LP tokens (lock/burn/vest) is declared pre-launch.

\textbf{Canonical pool commitment:} The launch precommits a hash of LP parameters (token mints, fee tier, initial price ratio, pool program) and the expected pool address derivation. The deploy transaction verifies the commitment before initializing, preventing fake-pool front-runs.

\textbf{Timeout \& fallback randomness:} If VRF is unavailable or the window elapses without execution, a timeout permits either a repeat draw or a commit-reveal fallback with anti-grinding rules and fixed deadlines.

\subsection*{Built-in Anti-Snipe}
Because allocations are decided before trading, launch-time sniping impact on the initial distribution is materially reduced; price MEV on the first blocks of listing can still occur. Randomised LP timing further reduces coordinated bot positioning. Optionally, airdrop claims can open only post-LP to eliminate pre-LP leakage.

\subsection*{Liquidity Bootstrapping Purchase (LBP) \& Redistribution}
A bounded LBP purchase may occur at LP creation with strict max-spend and slippage guards. Public limits include: (i) max percent of initial LP tokens, (ii) max base budget, (iii) optional no-sell period N days for LBP-held tokens. Purchases use a public vault address; receipts and post-trade balances are emitted on-chain. Tokens from LBP route to quest rewards, cross-platform airdrops, or partner campaigns.

\subsection*{Lumi Revenue Model \& Xyber Buyback}
Lumira receives a small protocol allocation $A_{\text{lumi}}$ of each launch's supply. Platform fees (creation, settlement, LP deploy) route 100\% to market-buy Xyber through a public route; execution transactions and amounts are emitted via events for transparency.

\subsection*{Agent-Optional Launches}
Agents are modular and permissioned: they can schedule quests, run micro-airdrops, propose governance changes, and triage community support. Launches function with or without agents.

\section*{On-Chain Architecture (MVP)}
\textbf{Programs / Contracts}
\begin{itemize}
  \item \textbf{FundingPool:} Stores $H$, $C$, $\tau$, LP window, status; accepts deposits; mints ticket receipts.
  \item \textbf{RandomSelection:} Pulls VRF proof; samples $K$ tickets; emits approvals and prepares refunds.
  \item \textbf{AirdropVault:} Holds project tokens; maps $a_i$ to token amounts; enforces vesting if enabled.
  \item \textbf{LPDeployer:} Precommits LP params; after $t^\ast$, enables permissionless LP initialization.
  \item \textbf{FeeCollector \& Buyback:} Accrues fees; executes Xyber buybacks; emits accounting events.
  \item \textbf{EngagementHub:} Quest registry, scoring, proof adapters, reward bridges.
  \item \textbf{AgentHub (optional):} Rate-limited actions with human override and audit log.
\end{itemize}

\section*{Algorithms (Pseudocode)}

\subsection*{Deposit \& Ticketization}
\begin{code}
function deposit(wallet, amount):
  require(state == FundingOpen)
  require(deposited[wallet] + amount <= C)
  deposited[wallet] += amount
  tickets_new = floor(deposited[wallet] / tau) - tickets_issued[wallet]
  tickets_issued[wallet] += tickets_new
  mint TicketReceipts(wallet, tickets_new)
\end{code}

\subsection*{Randomised Allocation}
\begin{code}
function run_selection():
  K = floor(H / tau)
  N = total_tickets()
  if N <= K:
    approve all tickets; finalize
  else:
    seed = get_vrf_seed()
    winners = sample_without_replacement(N, K, seed)
    for each wallet i:
      y_i = count_winner_tickets(wallet i)
      a_i = y_i * tau
      approve(wallet i, a_i)
      refund(wallet i, deposited[i] - a_i)  // includes < tau remainder
\end{code}

\subsection*{Airdrop Calculation}
\begin{code}
function compute_airdrop(wallet i):
  tokens_i = (approved[i] / total_approved) * A_airdrop
\end{code}

\subsection*{Randomised LP Deployment}
\begin{code}
function schedule_lp():
  (start, end) = LP_window
  seed2 = get_vrf_seed()         // distinct or derived
  t* = start + (seed2 mod (end - start))
  store t*
function deploy_lp():
  require(blocktime >= t*)
  initialize_pool(token_LP, base_LP, slippage_guard)
\end{code}

\section*{Parameter Guidance}
\begin{itemize}
  \item Ticket size $\tau$: target 1--5\% of $C$ to balance granularity vs. on-chain state.
  \item Max tickets $N_{\text{max}}$: enforce an upper bound to cap compute/time; refunds always return any remainder $<\tau$.
  \item LP window: 4--24h typical; wider windows reduce coordination risk but delay price discovery.
  \item Refunds: pull-model with clear claim UI; consider a claim-deadline reminder but do not reappropriate funds automatically.
\end{itemize}

\section*{Security, Fairness \& Risk}
\begin{itemize}
  \item \textbf{Verifiable randomness:} Chain-native VRF or beacon; no blockhash-only RNG.
  \item \textbf{Uniform ticket fairness:} Selection uniform at ticket level; contribution helps only up to $C$.
  \item \textbf{Sybil resistance (optional):} Allowlists, liveness checks, social graph scoring, identity staking.
  \item \textbf{Economic guardrails:} Pull-then-push refunds with re-entrancy guards; LP slippage bounds; bounded LBP purchase.
  \item \textbf{LP token policy:} Lock/burn/vest per precommitted policy to mitigate rug risk.
  \item \textbf{Upgrades \& observability:} Timelocked upgrades; exhaustive event logs; emergency pause to safe refund states only.
  \item \textbf{Canonical pool commitment:} Precommitted hash and address verification to block fake-pool attacks.
  \item \textbf{Fallback randomness:} Commit-reveal with anti-grinding as a reserve path if VRF is unavailable.
  \item \textbf{LP tokens default:} Protocol-owned LP tokens locked for 90 days; custody via multisig; events LPLocked/LPUnlocked emitted.
\end{itemize}
